# BE200 development notes

This branch adds Intel Wi-Fi 7 (BE family) support to the native Tahoe/Sequoia
`AirportItlwm` from [laobamac/itlwm](https://github.com/laobamac/itlwm). Linux
iwlwifi (`mvm`, `mld`) and mac80211 are the behavioural reference for every
firmware command and protocol step; OpenBSD `if_iwx`/net80211 is the code base
it is written in.

## Hardware and firmware selection

PCI IDs `272b` (BE200/BE202, Killer BE1750 x/w, discrete GL transport) and
`a840`, `7740`, `4d40` (BE201, Killer BE1750 i/s, integrated BZ transport) are
matched. MAC/RF revision, stepping and CDB generate the firmware prefix as in
Linux v6.12 `iwl_pci_find_dev_info()`; a candidate needs both its uCode and its
paired PNVM.

| Hardware prefix | Adapted APIs | Default |
|---|---|---|
| `iwlwifi-gl-c0-fm-c0` | 92, 86 | 92 |
| `iwlwifi-bz-b0-fm-c0` | 92 | 92 |
| `iwlwifi-bz-b0-gf-a0` | 92 | 92 |

The highest adapted API is tried first; a candidate that fails to load moves to
the next one for the same prefix. `itlwm_gl_api=86` limits GL to API 86.
Command wire formats follow the firmware's command-version TLV table.

Boot arguments: `itlwm_he=1` enables HE/EHT (BZ MLD command path only; 320 MHz
needs UHB and the matching firmware APIs), `itlwm_cc=XX` sets a preferred
country code.

## Connection pipeline

Each stage lists where it lives and its Linux reference. "Hardware" means
observed on a BE200 with real traffic; everything else is source-level only.

| Stage | Code | Linux reference | Status |
|---|---|---|---|
| Scan: PSC/RNR-hinted 6 GHz channels, short SSID, dwell | `iwx_umac_scan_v17`, `ieee80211_collect_scan_rnr` | `mld/scan.c` | Hardware (6 GHz networks listed) |
| Results to WCL, BSS selection | `publishWCLBeacon`, `postWCLScanResult` | (Apple WCL) | Hardware |
| Join request, AKM selection | `startWCLJoin`, `ieee80211_choose_rsnparams` | `mac80211/mlme.c` | Hardware (WPA2, WPA3) |
| SAE (H2E and hunting-and-pecking) | `ieee80211_sae.c`, `ieee80211_auth_sae` | `hostapd` SAE | Hardware: 6 GHz SAE/H2E |
| Association request: HE/EHT capabilities, Basic MLE | `ieee80211_get_assoc_req`, `ieee80211_add_mld_assoc_req` | `mac80211/mlme.c` | Hardware for single link; MLE unverified |
| Affiliated link discovery: ML probe at join, per-STA profile expansion, link usability | `iwx_fill_probe_req`, `ieee80211_recv_ml_probe_resp`, `ieee80211_mld_discover_links` | `wpa_supplicant_connect_ml_missing()`, `cfg80211_parse_ml_elem_sta_data()`, `wpa_bss_get_usable_links()` | Unverified |
| Association response, accepted links | `ieee80211_mld_assoc_response_links` | `mac80211/mlme.c` | Unverified |
| Firmware MAC/LINK/STA setup per link | `iwx_mld_auth`, `iwx_mld_run`, `iwx_mld_add_sta_cmd` | `mld/iface.c`, `mld/link.c`, `mld/sta.c` | Hardware for one link |
| Keys (PTK, GTK, IGTK, BIGTK) | `iwx_mld_set_key` | `mld/key.c` | Hardware: PTK/GTK |
| Rate control, A-MPDU, A-MSDU | `iwx_rs_init`, `iwx_rs_update`, `iwx_tx_amsdu` | `mld/tlc.c`, `pcie/tx-gen2.c` | Hardware: 6 GHz ~750 Mbit/s; TX A-MSDU fixed after Fix30, unverified |
| Active links, eMLSR, TTLM | `iwx_mld_update_active_links`, `iwx_mld_select_links`, `iwx_mld_tpt_task`, `iwx_ttlm_apply` | `mld/mlo.c`, `mac80211/mlme.c` | Unverified |
| Reporting to macOS (channel, width, PHY, rates) | `getWCL_BSS_INFO`, `copyWCLExtendedBss` | (Apple WCL) | Partially wrong in Fix29 (6 GHz width shown as 20 MHz); later fix unverified |

The join scan for an AP MLD probes the target BSSID with a Multi-Link probe
request, so the other links are known from the ML probe response even after
the node table was flushed; a link is used when it shares the chosen AKM and
pairwise cipher, has MFP and matches the MLD/EML capabilities. The kernel log
shows each reported link (`ieee80211_recv_ml_probe_resp: link N of ...`).
All accepted links are configured and the link of the join is active at first.
The BE200 is a single-radio eMLSR device: two links are active only as an EMLSR
pair, which carries traffic on one link at a time, so the links' rates are not
added up. The firmware never recommends entering EMLSR (iwlmld logs that as
unexpected), so the driver decides, as `iwl_mld_select_links()` does: EMLSR is
blocked until the traffic reaches 400 MPDUs in a 5 s window, the secondary links
are then probed again, links are graded by RSSI, channel load (periodic
firmware statistics, BSS Load for a link not in use) and punctured share of the
channel, and the best pair of any two links is entered when the AP offers EMLSR,
the bands differ and the RSSI and width rules hold. The better link is the
primary and has to be on the air, since only its measured load counts. Without
a pair the best single link is selected. EMLSR is left on low RSSI, low channel
load, a firmware request or a failed transition, keeping the better of the two
links, and the driver waits 30 s (300/600 s on repeats) before trying again. A
choice of the policy that the firmware refuses is rolled back and retried later;
it does not drop the association. STR is not implemented. EAPOL, management and
data frames use the primary link. macOS is told the BSSID, channel and signal
of the active link. The kernel log reports the links after association and
every active-link change (`active links 0x.. -> 0x..`).

Differences from iwlmld, all unverified on hardware: exit for low link usage is
omitted because received frames are not attributed to a link; the 6 GHz RSSI
correction is the fixed 4 dB iwlmld falls back to, without its duplicate-beacon
and PSD/EIRP estimates; the channel load of a link not in use is its BSS Load
element or the per-band default; rates and MCS shown to macOS still come from
the first link.

## Diagnostics

The PCI device carries only what a community report needs to identify a
firmware failure:

- `AirportItlwm-FirmwareErrorCount`, `-FirmwareErrorLmac`, `-FirmwareErrorUm`,
  `-FirmwareErrorDriver`: the error tables of the last firmware assert.
- `AirportItlwm-Diagnostic00`–`31`, `-DiagnosticSequence`: a ring of driver
  events (recovery, init/stop, command and state errors).
- `AirportItlwm-FirmwarePrefix`, `-FirmwareAPI`, `-PNVMName`,
  `-FirmwareCandidateIndex`: the selected firmware.

`scripts/Collect-WiFi-Community.command` records these together with the kernel
and airportd logs around one reproduced attempt.

## Build

The workflow builds Tahoe and Sequoia x86_64 kexts against MacKernelSDK
`3f750085caa17ec3a7880f11c11bf4f48cd6a164`. The pinned SDK predates the public
MSI-X declaration, so `scripts/prepare_tahoe_sdk.py` checks the header hash and
exposes Apple's `IOPCIDevice::configureInterrupts` in reserved slot 3
([Apple's header](https://github.com/apple-oss-distributions/IOPCIFamily/blob/main/IOKit/pci/IOPCIDevice.h)).

```sh
python3 scripts/prepare_tahoe_sdk.py
xcodebuild -project itlwm.xcodeproj -scheme AirportItlwm-Tahoe \
  -configuration Debug ARCHS=x86_64 CODE_SIGNING_ALLOWED=NO build
```

A build is not a hardware result.
