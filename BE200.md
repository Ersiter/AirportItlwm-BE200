# BE200 development

## BE family firmware selection (Fix29, 2026-11-03)

The experimental hardware path covers BE200 and BE202 with discrete GL transport,
and BE201 with integrated BZ transport. Killer BE1750 x/w follows the BE200 GL
path; BE1750 i/s follows the BE201 BZ path. Integrated BZ requires the matching
host CNVio platform.

PCI IDs `272b`, `a840`, `7740` and `4d40` select the transport. MAC/RF revisions,
stepping and CDB then generate the firmware prefix. BZ stepping and blank RF-ID
recovery follow Linux v6.12's CNVI/CRF/OTP mapping. A candidate requires both its
uCode and paired PNVM resource; PNVM contents retain the existing SKU/MAC/RF
matching during initialization.

| Shipped hardware prefix | Adapted API candidates | Default |
|---|---|---|
| `iwlwifi-gl-c0-fm-c0` | 92, 86 | 92 |
| `iwlwifi-bz-b0-fm-c0` | 92 | 92 |
| `iwlwifi-bz-b0-gf-a0` | 92 | 92 |

Automatic selection tries the highest adapted API for every hardware prefix.
`itlwm_gl_api=92` retains that order; `itlwm_gl_api=86` limits GL to API 86.
Each candidate must pass resource lookup, firmware parsing, API identity and the
adapted PHY/LINK/MAC/STA/key/queue/BA/RLC command versions. A failed candidate
advances within the same hardware prefix. Memory allocation and busy errors
propagate to the caller. Unsupported prefixes report the missing resource pair.
Linux v6.12's 90-93 range is the upstream reference; this driver selects the
explicitly adapted APIs in the table above.

GL86 and GL92 retain their existing firmware/PNVM pairs. BZ92 and its FM/GF PNVM
resources come from linux-firmware commit
`a21b7f3e500b13ac168788ac638e85db66c338dc`. `tests/be_firmware.json` records the
names, sizes, SHA-256 hashes and provenance. Runtime identity is exposed through
`AirportItlwm-FirmwarePrefix`, `AirportItlwm-FirmwareAPI`,
`AirportItlwm-PNVMName` and `AirportItlwm-FirmwareCandidateIndex`.

Firmware section capacity is 73: GL86 uses 70 sections, GL92 71, BZ/FM92 73 and
BZ/GF92 68. The production section storage and grouping tests verify every image
and its context DMA limits. `scripts/check_be_firmware.py` executes the production
selection/loader path with sanitizers, checks the real firmware command tables,
and verifies both platform PCI personalities. These checks run locally and are
included in the build workflow. Cross-model radio initialization, association,
MLO, throughput and stability require hardware validation.

## 6 GHz HE, beacon tracking and country recovery (Fix29, 2026-11-04)

A Wi-Fi 7 test capture confirms 6 GHz WPA3 SAE authentication, the EAPOL
handshake and DHCP. The connection then loses beacons after approximately
36 seconds. Its effective country remains US during that interval. The capture
also records a separate earlier firmware recovery with the world domain.

The HE 6 GHz capability flag shared a bit with EHT operation state. Updating
EHT state cleared the HE prerequisite, which prevented 6 GHz HE negotiation
and left the PHY at legacy 20 MHz. The flags now have independent bits.
Nontransmitted MBSSID profiles now set the reference BSSID and BSSID index in
every LINK update, including updates made before HE negotiation. This follows
[Linux v6.12 link configuration](https://github.com/torvalds/linux/blob/v6.12/drivers/net/wireless/intel/iwlwifi/mvm/link.c).

Country recovery retains the last resolved firmware country across a world
response. A valid `itlwm_cc` preference takes priority over subsequent country
requests. Native country hints use two validated letters and terminated storage;
world placeholders leave the saved hint intact. Country reporting and channel
permissions continue to follow the firmware response. The existing protection
against Wi-Fi hints changing an associated link remains active.

`scripts/check_6ghz_state.py` runs the production HE parsers, negotiation, LINK
formatter and country policy with AddressSanitizer/UndefinedBehaviorSanitizer.
It covers 20/40/80/160 MHz negotiation, regulatory narrowing, MBSSID reference
fields and country restore/request/report behavior. The local regression suite
passes, including SAE 95/99 cases. Sustained connectivity, negotiated width and
country preference acceptance remain pending physical testing of this revision.

## 6 GHz interoperability follow-up (Fix29, 2026-11-04)

Automatic BE selection now starts at API 92 for every shipped prefix, with API
86 as the adapted GL fallback. Each candidate keeps its hardware prefix and
paired PNVM; explicit API limits remain available for diagnostics.

OWE group 19 EAPOL descriptor version 0 uses HMAC-SHA-256 truncated to 16 bytes,
with a 16-byte KCK, as specified by [RFC 8110](https://www.rfc-editor.org/rfc/rfc8110.html).
SAE retains AES-CMAC for descriptor version 0. Independent P-256, PMK/PTK and MIC
vectors verify both paths and rejection of a modified EAPOL frame.

6 GHz scans use the upstream active/passive dwell defaults of 10/110 TU and
retain adaptive dwell. Associated scans use 120 TU away / 120 TU home, or
44/95 TU fragmentation for short latency budgets. The previous 250 TU override
was withdrawn after checking [Linux v6.12 scan timing](https://github.com/torvalds/linux/blob/v6.12/drivers/net/wireless/intel/iwlwifi/mvm/scan.c)
and [upstream PR #33](https://github.com/laobamac/itlwm/pull/33). These are
per-channel and scheduling budgets; a full scan spans multiple channels.

Live EHT operation and puncturing survive Beacon/association IE omissions.
Validated replacement operations reset fields that are absent in the replacement.
HE rate masks and TLC flags use the selected link's peer capabilities. Aggregated
TX completion accepts every active MLD station, so secondary-link queues can be
reclaimed. Country-code changes refresh the native cache even when the firmware
reports an unchanged channel profile. HE negotiation failures log capability,
policy and MCS inputs for the failed association.

The supplied capture uses the preceding revision and records a 6 GHz legacy
20 MHz association with EAPOL completion and DHCP. Sustained 6 GHz connectivity,
OWE interoperability, 160/320 MHz operation and throughput remain hardware test
items for this revision. Whole-machine freezes under heavy transfer remain an
open investigation; the capture contains no freeze-time execution stack.

Two earlier shutdown-stall reports contain APFS sampling frames, with USB/SCSI

lists; their UUIDs have zero entries in the decoded frame tables. These are

a matching event timeline and thread wait-chain analysis.

[Upstream PR #44](https://github.com/laobamac/itlwm/pull/44) proposes waiting for
scan abort completion and republishing current-request BSS metadata before scan
completion to meet short result-age limits. This branch remains under comparison
with the local batching and completion lifecycle.

[KGP Alpha 2](https://github.com/kgp-macPro/AirportItlwm-Tahoe/releases/tag/v1.2.0-be200-alpha.2)
reports substantially improved BE200 throughput after QoS/per-TID queue and RX
credit changes, using its legacy wireless frontend and 5 GHz test environment.
Local RX already returns credits before upper-stack callbacks and handles
zero-progress TX completions. Local TX retains a host ADDBA flow, so firmware BA
ownership needs a separate queue/header comparison. The selected sources are
[ee7e6e42](https://github.com/kgp-macPro/AirportItlwm-Tahoe/commit/ee7e6e42c5ad8a05151dadaf88cd14d8749fc9ee)
and [AirportBZ](https://github.com/HuajiFruit/AirportBZ/blob/0ccab1627764406861fb9eb0a06ca36e31b4440f/itlwm/hal_iwx/ItlIwx.cpp).

Linux also merged [restart-time TX gating](https://github.com/torvalds/linux/commit/2becb38a3e217ef2b2f42fddd7db7a25905ec291)
and [a TSO segmentation fix](https://github.com/torvalds/linux/commit/92cee08dc4f00e77fd1317e4343c5d458b0abab7).
The driver now stops TX dequeue and direct submissions while firmware is failed,
shutting down or radio-killed. BZ RX returns credits before upper-stack handoffs
in groups of at most 32 completions, retaining reset-generation and reentry
checks. The Linux TSO change applies to its GSO path; this driver uses a separate
transmit path.

WCL scan replacement now requests an explicit hardware restart and waits for
terminal abort completion. Old completion events are filtered by that lifecycle
state. A scan has one 20-second request budget; the latest metadata per BSSID
and band/channel is retained for the request and posted before successful
completion. Deferred requests keep a deadline, and cached results are released
on completion, cancellation and shutdown. Active/passive dwell remains 10/110 TU.

Production-function tests exercise replacement/background scans, abort waits,
reset generations, BSS freshness and cache ownership, TX queue preservation and
bounded RX handoffs. Local AddressSanitizer checks pass. Whole-machine freeze,
sustained throughput and radio behavior require physical validation of the new
build.

### User-authorized scope expansion (2026-10-25)

The user expanded the original WPA2 milestone to include PMF/BIGTK and Wi-Fi 7/MLO. The current source changes extend the BZ MLD security-key path for BIP-CMAC-128, BIP-GMAC-128/256 IGTK, and BIGTK IDs 6/7; they parse the group-management cipher and KDE sizes, map GMAC keys to Intel GCMP firmware flags, and require firmware key-valid, MIC-valid, and replay-clear status on the hardware-offloaded GMAC IGTK and BIGTK Beacon paths. BIP-GMAC is enabled only when the BZ MLD SEC_KEY v1 path is available; BIGTK additionally requires firmware BIGTK capability 100. The receive path now avoids sending unprotected BIP frames through the CCMP PN/IV handler.

References used: Intel Linux [MLD key setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/key.c) maps AES-CMAC to CCMP and BIP-GMAC-128/256 to GCMP (including the 256-bit key-size flag), with IGTK marked MFP and station group keys marked multicast/no-TX. Its [management receive path](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mvm/rxmq.c) checks the firmware key-valid, MIC, replay, and cipher-specific MMIE/key-ID state. For HE on the BZ MLD API, use Intel Linux's [MLD link setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/link.c), [association handling](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/mac80211.c), and [per-link station setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/sta.c) as the behavioral references. laobamac open PRs #29 (PMF), #26 (early EAPOL/WCL authorization race), and #11 (ASSOC→RUN link-state preservation) were reviewed as targeted references; #29's PMF fix and the two existing local state-path changes are relevant, while the other PR-specific changes were not copied without a matching local failure. The PRs are open proposals, not merged upstream implementations.

The VM macOS 26.4 Debug x86_64 build succeeded on 2026-10-25 after these changes. This is compile evidence only; the VM has no BE200 radio, and this source build was not deployed to F EFI. No association, EAP, key handshake, DHCP, or RF behavior was tested.

`itlwm_he=1` is the generic HE opt-in. This pass now connects that existing capability profile to the BE200 BZ MLD API. `iwx_setup_he_rates()` accepts the BZ MAC/LINK/STA command versions without requiring the legacy `STA_HE_CTXT_CMD`; `MAC_CONFIG_CMD` publishes HE support and the NIC ACK capability; after association, `LINK_CONFIG_CMD` receives the AP's default packet extension, RTS threshold, BSS color, and MU-EDCA; `STA_CONFIG_CMD` receives the negotiated AP HTC, PPE, ACK, and HE A-MPDU settings. `iwx_mld_auth()` clears negotiated HT/VHT/HE state before association, while the validated HE capability/operation IEs remain for the association request and response negotiation. The MLD API choice itself still does not mean the AP association negotiated MLO. Implementation follows Intel Linux v6.15 [MLD MAC setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/iface.c), [link setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/link.c), and [station setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/sta.c).

Intel's BE200 product specification confirms Wi-Fi 7 and MLO using eMLSR. This is the hardware target; the gaps below are in this Darwin driver's interface and command integration, not in the adapter's Wi-Fi 7 capability. [Intel BE200 specifications](https://www.intel.com/content/www/us/en/products/sku/230078/intel-wifi-7-be200/specifications.html)

The EHT/MLO source path now builds the Basic MLE and per-STA Association Request profiles, parses accepted profiles from the response, and maps AP Link IDs separately from local/firmware link slots. Each accepted link receives its own PHY context, STA, TLC rate configuration, and firmware link context; common keys cover the configured MLD STA mask, RX BAID masks and TX queue masks follow the active-link set, RX selects the AP link node by BSSID, and data TX uses that active link's AP/local MAC addresses. EHT 160/320 MHz uses CCFS1 for the PHY center; the v1 link command receives the negotiated EHT puncture mask. Intel's BZ API supports at most two active links per VIF, so all accepted links are configured but only the anchor is initially active; eMLSR can select a two-link pair when both peers advertise support and the links meet the upstream band/width/RSSI criteria. EAPOL and management traffic stay on the selected primary link. This implements the BE200 eMLSR path; STR is not claimed. The 26.7 WCL candidate supplies the AP MLD address at offset `0x1d7` with flag `0x80` at `0x1e0`; the peer MLD address and AP link address remain separate in `STA_CONFIG_CMD`. The Debug x86_64 VM build passes, but the VM has no BE200 radio, so association, EAP, keys, DHCP, and RF behavior remain unverified.

Inspect the PCI parent in IORegistry for `AirportItlwm-PNVMStatus` and
`AirportItlwm-PNVMPayloadLength`. `0xFFFFFFFF` means pending or unavailable;
a valid four-byte status of `0xFFFFFFFF` is distinguished by payload length 4.

The original hardware baseline is Intel BE200 PCI `8086:272B`, subsystem
`8086:00F4`, on x86_64 macOS Tahoe 26.4 / Darwin 25.4.0. Current experimental

## Build

Use the **BE200 Tahoe build** workflow with the Debug or Release configuration.
It builds the source in this repository, using MacKernelSDK commit
`3f750085caa17ec3a7880f11c11bf4f48cd6a164`. Jobs have a 20-minute timeout.
Source changes on the development branch also trigger one Debug build.
Artifacts and compiler logs are retained for 7 days. Builds are not physical
validation and are not automatically published as releases.

The pinned SDK predates the public MSI-X declaration. The preparation script
checks its exact header hash, then replaces the reserved virtual slot with
Apple's `IOPCIDevice::configureInterrupts` declaration. This dependency patch
is for the Tahoe target. It does not modify a system framework or kernel.
See [Apple's header](https://github.com/apple-oss-distributions/IOPCIFamily/blob/main/IOKit/pci/IOPCIDevice.h)
for the slot and API signature.

The local commands are:

```sh
python3 scripts/prepare_tahoe_sdk.py
xcodebuild -project itlwm.xcodeproj -scheme AirportItlwm-Tahoe \
  -configuration Debug ARCHS=x86_64 CODE_SIGNING_ALLOWED=NO build
```
