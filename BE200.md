### User-authorized scope expansion (2026-10-25)

The user expanded the original WPA2 milestone to include PMF/BIGTK and Wi-Fi 7/MLO. The current source changes extend the BZ MLD security-key path for BIP-CMAC-128, BIP-GMAC-128/256 IGTK, and BIGTK IDs 6/7; they parse the group-management cipher and KDE sizes, map GMAC keys to Intel GCMP firmware flags, and require firmware key-valid, MIC-valid, and replay-clear status on the hardware-offloaded GMAC IGTK and BIGTK Beacon paths. BIP-GMAC is enabled only when the BZ MLD SEC_KEY v1 path is available; BIGTK additionally requires firmware BIGTK capability 100. The receive path now avoids sending unprotected BIP frames through the CCMP PN/IV handler.

References used: Intel Linux [MLD key setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/key.c) maps AES-CMAC to CCMP and BIP-GMAC-128/256 to GCMP (including the 256-bit key-size flag), with IGTK marked MFP and station group keys marked multicast/no-TX. Its [management receive path](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mvm/rxmq.c) checks the firmware key-valid, MIC, replay, and cipher-specific MMIE/key-ID state. For HE on the BZ MLD API, use Intel Linux's [MLD link setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/link.c), [association handling](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/mac80211.c), and [per-link station setup](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/intel/iwlwifi/mld/sta.c) as the behavioral references. laobamac open PRs #29 (PMF), #26 (early EAPOL/WCL authorization race), and #11 (ASSOC→RUN link-state preservation) were reviewed as targeted references; #29's PMF fix and the two existing local state-path changes are relevant, while the other PR-specific changes were not copied without a matching local failure. The PRs are open proposals, not merged upstream implementations.

The VM macOS 26.4 Debug x86_64 build succeeded on 2026-10-25 after these changes. This is compile evidence only; the VM has no BE200 radio, and this source build was not deployed to F EFI. No association, EAP, key handshake, DHCP, or RF behavior was tested.

`itlwm_he=1` is the generic HE opt-in. This pass now connects that existing capability profile to the BE200 BZ MLD API. `iwx_setup_he_rates()` accepts the BZ MAC/LINK/STA command versions without requiring the legacy `STA_HE_CTXT_CMD`; `MAC_CONFIG_CMD` publishes HE support and the NIC ACK capability; after association, `LINK_CONFIG_CMD` receives the AP's default packet extension, RTS threshold, BSS color, and MU-EDCA; `STA_CONFIG_CMD` receives the negotiated AP HTC, PPE, ACK, and HE A-MPDU settings. `iwx_mld_auth()` clears negotiated HT/VHT/HE state before association, while the validated HE capability/operation IEs remain for the association request and response negotiation. The MLD API choice itself still does not mean the AP association negotiated MLO. Implementation follows Intel Linux v6.15 [MLD MAC setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/iface.c), [link setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/link.c), and [station setup](https://github.com/torvalds/linux/blob/v6.15/drivers/net/wireless/intel/iwlwifi/mld/sta.c).

Intel's BE200 product specification confirms Wi-Fi 7 and MLO using eMLSR. This is the hardware target; the gaps below are in this Darwin driver's interface and command integration, not in the adapter's Wi-Fi 7 capability. [Intel BE200 specifications](https://www.intel.com/content/www/us/en/products/sku/230078/intel-wifi-7-be200/specifications.html)

The EHT/MLO source path now builds the Basic MLE and per-STA Association Request profiles, parses accepted profiles from the response, and maps AP Link IDs separately from local/firmware link slots. Each accepted link receives its own PHY context, STA, TLC rate configuration, and firmware link context; common keys cover the configured MLD STA mask, RX BAID masks and TX queue masks follow the active-link set, RX selects the AP link node by BSSID, and data TX uses that active link's AP/local MAC addresses. EHT 160/320 MHz uses CCFS1 for the PHY center; the v1 link command receives the negotiated EHT puncture mask. Intel's BZ API supports at most two active links per VIF, so all accepted links are configured but only the anchor is initially active; eMLSR can select a two-link pair when both peers advertise support and the links meet the upstream band/width/RSSI criteria. EAPOL and management traffic stay on the selected primary link. This implements the BE200 eMLSR path; STR is not claimed. The 26.7 WCL candidate supplies the AP MLD address at offset `0x1d7` with flag `0x80` at `0x1e0`; the peer MLD address and AP link address remain separate in `STA_CONFIG_CMD`. The Debug x86_64 VM build passes, but the VM has no BE200 radio, so association, EAP, keys, DHCP, and RF behavior remain unverified.

`AirportItlwm-PNVMPayloadLength`. `0xFFFFFFFF` means pending or unavailable;
a valid four-byte status of `0xFFFFFFFF` is distinguished by payload length 4.

Target: Intel BE200 PCI `8086:272B`, subsystem `8086:00F4`, on x86_64 macOS
Tahoe 26.4 / Darwin 25.4.0. The target is BE200 Wi-Fi 7, including eMLSR MLO.
HE/EHT are exposed only on the supported BZ MLD command path with `itlwm_he=1`;

## Build

Use the **BE200 Tahoe build** workflow with the Debug or Release configuration.
It builds the source in this repository, using MacKernelSDK commit
`3f750085caa17ec3a7880f11c11bf4f48cd6a164`. Jobs have a 20-minute timeout.
Source changes on the development branch also trigger one Debug build.
Artifacts and compiler logs are retained for 7 days. Builds are not physical
validation and are not automatically published as releases.

The pinned SDK predates the public MSI-X declaration. The preparation script
checks its exact header hash, then replaces the reserved virtual slot with
Apple's `IOPCIDevice::configureInterrupts` declaration. This dependency patch
is for the Tahoe target. It does not modify a system framework or kernel.
See [Apple's header](https://github.com/apple-oss-distributions/IOPCIFamily/blob/main/IOKit/pci/IOPCIDevice.h)
for the slot and API signature.

The local commands are:

```sh
python3 scripts/prepare_tahoe_sdk.py
xcodebuild -project itlwm.xcodeproj -scheme AirportItlwm-Tahoe \
  -configuration Debug ARCHS=x86_64 CODE_SIGNING_ALLOWED=NO build
```

These are Intel firmware binaries, distributed under [Intel's firmware license](iwlwifi-firmware-license).

| Input | SHA-256 |
|---|---|
| `iwlwifi-gl-c0-fm-c0-86.ucode` | `6b1e8d640327ca05b33830499a8ac356d12973d3f3ae550e2d86bdf80a53d736` |
| `iwlwifi-gl-c0-fm-c0.pnvm` | `f486587db1edde8791665dc27d263d907890fcdf16cc8f8fb254cacd360d4a6e` |

The initial firmware header reports API 86. Its command-version TLV table is
used to select wire structures; newer OpenBSD firmware structures are not
assumed to match this older firmware.

The GL-86 firmware's command-version table reports MCC_UPDATE `(group 1,
command 0xc8)` notification version 8. The current response parser follows
Linux v6.12 `iwl_mvm_update_mcc`: response versions 8 and later use the v8
layout, earlier responses use v4 when `MCC_UPDATE_11AX_SUPPORT` is present,
and otherwise use v3. A missing notification-version entry follows Linux's
lookup default of version 0 before applying the v4/v3 capability fallback.
Each layout has an exact bounded channel-array length
check before the existing channel map is updated. MCC status remains
diagnostic and does not introduce a new fatal policy. The v6.12 source and
wire structures are in [mvm/nvm.c](https://github.com/torvalds/linux/blob/v6.12/drivers/net/wireless/intel/iwlwifi/mvm/nvm.c#L414-L507) and
[fw/api/nvm-reg.h](https://github.com/torvalds/linux/blob/v6.12/drivers/net/wireless/intel/iwlwifi/fw/api/nvm-reg.h#L365-L393).
